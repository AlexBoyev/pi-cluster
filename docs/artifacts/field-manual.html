This document is a full-context handoff: current state, what's actually done vs. assumed, and where the open edges are.

Overview

Pi-Cluster is two things running on the same four Raspberry Pis: a DevOps admin platform (React + FastAPI, its own CI/CD, its own monitoring stack) that manages Kubernetes workloads on the cluster it runs on — and, riding on top of the K8s orchestration that platform built, a small set of household services (Wallabag, Vikunja, Paperless-ngx, Firefly III) gated behind single sign-on. All four originally-planned services are now live.

The platform is not a toy dashboard. It does real orchestration: deploy, scale, rolling image updates, HPA, node drain, live pod exec/log streaming, RBAC/Secret/ConfigMap/PVC management, alert-rule CRUD from the UI — all audit-logged, all backed by a real Postgres schema, all covering 310 backend tests. Current priority is operational hardening (backup/DR, log aggregation, image registry, retention), not new dashboard features — those are all already built; see Operational hardening.

Architecture

Two independent delivery pipelines feed the same node. Jenkins owns the Docker Compose stack; ArgoCD owns everything under k8s/apps/, recursively into every subdirectory. That last word is load-bearing: until 2026-09-07 the live ArgoCD Application had no directory.recurse set, so it silently applied only root-level files — every household service (Wallabag, Vikunja, Paperless) had been reachable purely through each one's manual kubectl apply fallback since it was first deployed, never actually through the automated path every doc described. Fixed live and in Terraform, which — separately — never even matched the live Application's real name/namespace to begin with; its true origin is still unknown (see Known gaps).

The SSO gate + auto-login bridge

Household services keep fully independent user systems — nothing talks to the platform's own users table. What's shared is reachability: nginx runs auth_request against the backend on every request to a household-service hostname, checking a dedicated pi_sso cookie set at platform login. No valid cookie, no route to Traefik at all.

Wallabag/Vikunja get a server-side auto-login bridge on top of the gate; Paperless and Firefly both use a trusted X-Pi-User header instead (PAPERLESS_ENABLE_HTTP_REMOTE_USER / remote_user_guard) — no stored credential at all, the same mechanism reused directly for the second service that supports it.

Household services

A deliberately separate category from the platform: self-hosted apps for two real people, gated but not identity-merged. Same repeatable pattern each time — one namespace, local-path storage pinned to a worker node, a dedicated Postgres role inside the existing database, a manually-created Secret (never in git — ArgoCD's selfHeal would fight it), and a plain Ingress on <name>.pi-cluster.lan.

Personal finance. CSV/OFX import via its Data Importer companion (its own Deployment); trusted-header SSO, no bridge; a K8s CronJob drives daily recurring-transaction processing. pi-node3.

Each new service has extended the pattern rather than just reused it: Vikunja needed a non-interactive CalDAV bypass and a per-user credential map instead of one shared login; Paperless needed a dedicated nginx block for trusted-header SSO and hostNetwork: true for real SMB port 445; Firefly reused Paperless's trusted-header block directly, unchanged, and added a second in-namespace Deployment pattern (the Data Importer) for a companion tool with its own lifecycle. All four originally-planned services are live — a fifth would need a new decision, not just a repeat of this pattern.

Bank-API integration: deliberately not attempted

Firefly's Data Importer supports automatic bank sync via GoCardless/Nordigen or SaltEdge, both PSD2 open-banking integrations — EU/UK-regulation-specific, with no basis to expect Israeli bank coverage. Documented as unavailable until proven otherwise rather than assumed to work. CSV export from the bank's own site, run through the Data Importer's manual mapping wizard, is the real working path — any bank, no cooperation needed.

Security

  • JWT Bearer auth, auto-refreshed by the frontend; every mutating route requires the admin role.
  • SSH credentials never reach the frontend or API responses — held only in backend environment variables.
  • Every workload/node operation is audit-logged with actor, timestamp, and result; audit_logs and resolved alert_history rows past LOG_RETENTION_DAYS (default 90) are purged daily.
  • Rate limited — 300 req/min per IP globally, 10/min on /auth/login; real client IP read from Cf-Connecting-Ip behind the Cloudflare Tunnel, not the tunnel's own loopback.
  • New-login-IP detection fires on every unrecognized IP for a user, unfiltered by severity — there's no "mildly urgent" version of a possible account compromise.
  • Infra alerts are severity-filtered per email channel (so HighCPU doesn't drown out a personal inbox); webhook channels stay unfiltered.
  • Alert-rule edits from the dashboard publish via a fine-grained GitHub PAT, Contents-write scoped to this one repo only.
  • Container registry has no auth — accepted, LAN-only posture, matching Prometheus/AlertManager's own LAN-restriction approach.

66

Cold-boot outage — 2026-09-07

18+ minute full outage after a full power cycle. First fix (a per-node k3s-agent boot-delay stagger) was reasonable but wrong — the real cause, found after the fix failed to prevent a reproduction, was Linux's uas driver hanging on the USB-SATA bridge behind all 4 nodes' SSDs on cold boot. Fixed with a kernel quirk (usb-storage.quirks=174c:235c:u) plus health probes on Traefik so a wedged pod can no longer report false-Ready. Same night: SSH key auth to pi-node3/4 root-caused (pi-node3 had no ~/.ssh at all) and a dnsmasq "restart loop" from earlier in the incident turned out to be a misdiagnosis — routine daily restarts misread from an untimestamped log tail. Full writeup in docs/decisions.md, including the correction.

67

Firefly III — fourth household service, completes the set

Deployed live and verified end-to-end, same ADR-first discipline as every prior service. Surfaced two real bugs bigger than Firefly itself: a too-short startupProbe caused a genuine restart-before-ready loop on first deploy, and — much bigger — ArgoCD had never actually recursed into k8s/apps/ subdirectories at all, meaning Wallabag/Vikunja/Paperless had silently never been GitOps-managed either, the entire time. Fixed for all four services at once. A third gap found after: the frontend's household-service tile array never got a Firefly entry despite its own comment saying to add one — Firefly was live and reachable by direct URL with zero dashboard link to it until caught.

Known gaps

What's genuinely open right now, not speculative — the honest state to plan from. Several items from the previous pass are gone because they turned out fixed, not because they were quietly dropped.

  • infra

    K3s datastore restore has never been drilled — the Postgres side of DR is proven live, the K3s SQLite side is not. Deliberately not attempted casually; stops the control plane's datastore, needs a scheduled window.

  • infra

    The live ArgoCD Application's real origin is unknown — neither terraform/argocd.tf nor ansible/playbooks/argocd.yml ever created the resource that's actually running, even after both were corrected to match its current spec. If it's ever deleted, no IaC path alone recreates it identically.

  • infra

    backend/tests/test_docs_consistency.py (the phase-drift guard) can only run against a full repo checkout — Jenkins's Test stage runs pytest inside the built backend Docker image, whose build context excludes docs/ and frontend/ entirely, so it skips there rather than actually checking. A real check, but a structural CI blind spot.

  • service

    Firefly's first admin account (via its setup wizard) and a real CSV import from an actual bank statement are both still unverified against live use — the deploy itself is confirmed, first real use isn't yet.

  • service

    Paperless's Cloudflare Tunnel public route status is unconfirmed as of this pass; Hebrew/Russian OCR accuracy and a real Samba client connection remain unverified against actual hardware.

Recommendations

The previous pass's #1 (hardening) and #2 (ship Firefly) are both substantially done — this is the updated set, reflecting that. Three directions, sequenced by risk and how much is already decided vs. still open.

01

Close the last two hardening loose ends

Infra

Everything from the previous round closed except two, and both are small: drill the K3s datastore restore for real (stop k3s, restore state.db, confirm the cluster comes back — needs a scheduled window, not a solo late-night attempt), and either accept or replace the ArgoCD Application's unknown origin — reverse-engineer how it was actually created and encode that in Terraform/Ansible for real, or deliberately decide "recreate it once from the corrected Terraform and treat that as the new source of truth" and do it.

Why this first, still: both are the same class of risk the 2026-09-07 incident and the ArgoCD-recurse discovery already proved out — an untested path that looks fine until it isn't. Small scope now, not a new investigation.
02

Finish onboarding Firefly, don't just leave it deployed

Follow-through

The deploy is verified — pods healthy, routing correct — but nobody has actually used it yet. Concretely: create the first admin account through the setup wizard (confirming live whether remote_user_guard wants username or email, still unverified either way), run one real CSV import from an actual bank statement through the Data Importer, and confirm Paperless's Cloudflare Tunnel route status while at it — it was flagged open in the same pass Firefly's route just got added.

Why this, not new work: a service that's "deployed" but never used for real hasn't actually validated the interesting parts of its own ADR (D1's CSV path, D2's auth-matching uncertainty) — those are exactly the assumptions worth confirming before trusting it with real financial data.
03

AI hooks — now the clear next initiative, not a placeholder

AI

With hardening nearly closed and all four household services live, this is genuinely what's next rather than one option among three. .env.example has carried placeholder ANTHROPIC_API_KEY/OPENAI_API_KEY entries since Wallabag's own ADR, reserved and never built. Stated direction is broad — "agent helpers/scanners/log conclusions/service assistants" — which argues for picking one concrete, bounded first target rather than a general framework: a Paperless enrichment worker (auto-tag/summarize OCR'd documents, its own pod, not baked into the container) is the best-scoped starting point, since the data (OCR text) already exists and the failure mode if it's wrong (a bad tag) is low-stakes compared to, say, an agent that acts on infra directly.

Why start narrow: "many AI components" is the eventual goal, but a log-summarizer, a service assistant, and an infra-scanning agent each have different trust levels (read-only vs. can-take-action) and different failure costs. Shipping one low-stakes, well-scoped worker first establishes the actual pattern (where does it run, how does it auth, what does "verified live" mean for an LLM call) before the second and third ones inherit it — the same incremental discipline every household service already used.
