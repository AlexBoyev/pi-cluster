Overview

Pi-Cluster is two things running on the same four Raspberry Pis: a DevOps admin platform (React + FastAPI, its own CI/CD, its own monitoring stack) that manages Kubernetes workloads on the cluster it runs on — and, riding on top of the K8s orchestration that platform built, a small set of household services (Wallabag, Vikunja, Paperless-ngx) gated behind single sign-on.

The platform is not a toy dashboard. It does real orchestration: deploy, scale, rolling image updates, HPA, node drain, live pod exec/log streaming, RBAC/Secret/ConfigMap/PVC management, alert-rule CRUD from the UI — all audit-logged, all backed by a real Postgres schema, all covering 310 backend tests. Current priority is operational hardening (backup/DR, log aggregation, image registry, retention), not new dashboard features — those are all already built; see Operational hardening.

Architecture

Two independent delivery pipelines feed the same node. Jenkins owns the Docker Compose stack; ArgoCD owns everything under k8s/apps/. One real exception: k8s/traefik/traefik.yaml looks GitOps-managed but isn't — ArgoCD's Application only watches k8s/apps/, so a change there needs a manual kubectl apply. This has bitten the project twice already (see Known gaps).

The SSO gate + auto-login bridge

Household services keep fully independent user systems — nothing talks to the platform's own users table. What's shared is reachability: nginx runs auth_request against the backend on every request to a household-service hostname, checking a dedicated pi_sso cookie set at platform login. No valid cookie, no route to Traefik at all.

Wallabag/Vikunja get a server-side auto-login bridge on top of the gate; Paperless uses PAPERLESS_ENABLE_HTTP_REMOTE_USER with a trusted X-Pi-User header instead — no stored credential at all.

Household services

A deliberately separate category from the platform: self-hosted apps for two real people, gated but not identity-merged. Same repeatable pattern each time — one namespace, local-path storage pinned to a worker node, a dedicated Postgres role inside the existing database, a manually-created Secret (never in git — ArgoCD's selfHeal would fight it), and a plain Ingress on <name>.pi-cluster.lan.

Each new service has extended the pattern rather than just reused it: Vikunja needed a non-interactive CalDAV bypass and a per-user credential map instead of one shared login; Paperless needed a dedicated nginx block for trusted-header SSO and hostNetwork: true for real SMB port 445. Both are documented as reusable for Firefly if it needs the same.

Security

  • JWT Bearer auth, auto-refreshed by the frontend; every mutating route requires the admin role.
  • SSH credentials never reach the frontend or API responses — held only in backend environment variables.
  • Every workload/node operation is audit-logged with actor, timestamp, and result; audit_logs and resolved alert_history rows past LOG_RETENTION_DAYS (default 90) are purged daily.
  • Rate limited — 300 req/min per IP globally, 10/min on /auth/login; real client IP read from Cf-Connecting-Ip behind the Cloudflare Tunnel, not the tunnel's own loopback.
  • New-login-IP detection fires on every unrecognized IP for a user, unfiltered by severity — there's no "mildly urgent" version of a possible account compromise.
  • Infra alerts are severity-filtered per email channel (so HighCPU doesn't drown out a personal inbox); webhook channels stay unfiltered.
  • Alert-rule edits from the dashboard publish via a fine-grained GitHub PAT, Contents-write scoped to this one repo only.
  • Container registry has no auth — accepted, LAN-only posture, matching Prometheus/AlertManager's own LAN-restriction approach.

66

Cold-boot outage — 2026-09-07

18+ minute full outage after a full power cycle. First fix (a per-node k3s-agent boot-delay stagger) was reasonable but wrong — the real cause, found after the fix failed to prevent a reproduction, was Linux's uas driver hanging on the USB-SATA bridge behind all 4 nodes' SSDs on cold boot. Fixed with a kernel quirk (usb-storage.quirks=174c:235c:u) plus health probes on Traefik so a wedged pod can no longer report false-Ready. Full writeup in docs/decisions.md, including the correction.

Recommendations

Three directions, in the order this document would prioritize them — not mutually exclusive, but sequenced by risk and how much of the existing pattern each one reuses.

01

Close the operational-hardening loop before adding anything new

Infra

The stated priority is already hardening, and it's 90% done — finishing it is cheaper than any new feature. Concretely: drill the K3s datastore restore (the one DR path never actually tested), move k8s/traefik/traefik.yaml into k8s/apps/ so it stops silently drifting from git, root-cause the dnsmasq restart loop and the pi-node3/4 key-auth failure, and add a CI check (or just a shared constant) so the sidebar's phase string can't drift from docs/roadmap.md again.

Why this first: every one of these is a known, named gap already sitting in this document — not a guess. The 2026-09-07 incident (Phase 66) is exactly what an untested edge case looks like when it becomes real; the K3s restore path is the same class of risk, just not yet triggered.
02

Ship Firefly III as the fourth household service

More services

Lowest-risk feature work available: the household-service pattern has now been proven three times, each time extending cleanly (SSO bridge → CalDAV exemption → trusted-header SSO) rather than breaking. Firefly III (personal finance) has been the named next service since Wallabag's own ADR — reuses the namespace/PVC/Postgres/Ingress pattern directly, and its own OAuth-style API might even avoid needing a bridge at all, closer to Paperless's trusted-header approach than Wallabag's shared-credential one.

Why this next: it's already the committed plan, not a new idea — and every prior service in this pattern has paid for itself by surfacing one more previously-invisible cluster bug (RBAC gaps, Promtail's zero-target scrape, a stale git clone). A fourth pass is likely to keep finding real infrastructure debt, which is directly useful for item 01.
03

Wire up the already-reserved AI hook — start with Paperless, not a new chat feature

AI

.env.example has carried placeholder ANTHROPIC_API_KEY/OPENAI_API_KEY entries since Wallabag's own ADR, explicitly reserved for "a future companion service" and never built. Paperless is the strongest fit for that hook to finally land: OCR text is already extracted and stored, so an enrichment worker (its own pod, not baked into the Paperless container) could call an LLM to auto-tag, summarize, or flag documents needing attention — a real capability gap Paperless doesn't natively have, not a chatbot bolted onto working infra.

Why this, not an ops-assistant panel: a natural-language "ask your cluster" dashboard feature is tempting but speculative — Prometheus/Loki/Grafana already answer those questions directly, so it would mostly restate existing UI. Document enrichment is a capability that doesn't exist today, was already scoped for, and doesn't touch anything the platform depends on to keep running if it's wrong.
